### corner_fusion: bug found + fixed, then first real numbers

Bug on the way to the first working run: the resubmitted smoke test showed
`selected` = `loma_H`/`samh_H` (never `fused_H`) and `fusion_modes` = all
`coast` on every frame/corner. Root cause: `TrackerConfig.model_copy(update=...)`
— how every `configs/tracker/*.py` composes a base config, including this
codebase's existing configs — does **not** re-run pydantic validators. The
base `loma_samh.py` config resolves `algorithm="loma_samh"` at construction;
`corner_fusion_alignh.py`'s `model_copy(update={"loma": ...fusion=True...})`
changed `loma.fusion` but left the already-resolved `algorithm` field
untouched, so the tracker silently ran the OLD hard-switch `loma_samh` code
for the whole run — the fusion code never executed, and the npz's `fused_H`
was NaN on literally every frame (the default un-run `TrackerDebugInfo()`).
Fix: set `"algorithm": "corner_fusion"` explicitly in the config's
`update=` dict (model_copy doesn't validate, so an explicit value isn't
cross-checked against the flag, it's simply used). Added a comment on the
`_resolve_algorithm` validator and two regression tests
(`test_fusion_flag_resolves_to_corner_fusion_algorithm`,
`test_corner_fusion_alignh_config_loads`) so this class of mistake — any
future flag that affects algorithm derivation, changed via model_copy
without also setting `algorithm` — fails loudly instead of silently running
the wrong algorithm. **General lesson for this config system**: whenever a
new config flips a flag that participates in `_derive_algorithm`, the
`algorithm` field must be set explicitly in the same `update=` dict.

**Root cause found for the regressions: unfloored covariance blow-up.**
Checked `fusion_max_disagreement` (squared Mahalanobis, should be O(1-10)
under any sane calibration) on the regressed vs improved sequences — both
groups show values up into the **thousands to hundreds of millions**
(Seq_00044: 74% of frames > 1e4, median 1.2e8). A near-collinear
correspondence set or a short boundary arc makes `(JᵀJ)⁻¹` return one
eigenvalue near zero — the branch reports itself as absurdly, wrongly
confident along that axis, which (a) makes the Mahalanobis disagreement
numerically meaningless and (b) — more damaging — makes the trace-based
"more confident branch wins" tie-break in `gated_confident` mode
untrustworthy: a degenerate, near-zero-trace covariance always "wins" the
comparison regardless of whether that branch is actually right. **Fixed**:
`corner_covariance._floor_cov_eigenvalues` (min credible std 0.25px — pixel
quantization + model-form error put a real floor under any fit's claimed
precision) applied at the point both `homography_corner_covs` and
`mask_align._corner_cov_from_boundary_fit` return their covariance stacks.
2 new unit tests. Full suite resubmitted (11325450). **This was flagged as
a real risk in docs/correction_research.md §9's own plan** ("both branches
are known to be overconfident in the field... needs calibration before
trusting the exact value") — I built fusion first and hit the predicted
failure mode empirically rather than calibrating first, but the fix is
narrow (a floor, not a full calibration campaign) and directly targets the
observed numerical pathology.

Rerun with the floor fix: p@15 80.47 (vs 80.44 unfloored) — **essentially
no change**. Confirms the floor wasn't the real issue (kept anyway, it's a
correct defensive fix for a genuine numerical pathology — near-singular
covariances producing nonsensical Mahalanobis values in telemetry — just
not the thing causing the regressions).

**Built the actual calibration check** the docs said should come first
(§9-10: "1. Calibration... 2. Normalized disagreement... 3. Fusion — only
if 1 and 2 hold up" — this session did 3 before 1/2 and hit exactly the
predicted failure mode). Added `fusion_loma_cov`/`fusion_samh_cov` to the
npz (packed (T,4,3) xx/xy/yy, `FusionTelemetry.loma_cov/samh_cov`,
`run.py`), reran the 20-seq probe to capture it, then compared each
branch's predicted corners against GT under its own covariance
(chi-square(2): median should be 1.386, 5% should exceed 5.99).

**Result: both branches are badly overconfident, and unevenly so.**
LoMa: median chi2 stat 44.0 (should be 1.4), 89% of frames exceed the 95%
tail (should be 5%) -> implied covariance inflation 31.8x. SAM-H: median
96.3, 92% over tail -> implied inflation 69.5x. **SAM-H is the more
overconfident of the two** (~2.2x more, in variance terms) — this directly
explains the regression pattern: the trace-based "more confident branch
wins" tie-break in `gated_confident` mode is systematically biased toward
SAM-H regardless of whether it's actually right, because its stated
confidence understates its true error more than LoMa's does. Heavy tails
persist after any uniform scale correction (99th-percentile chi2 stats in
the 1e5-1e8 range for both) — expected, that's the gross-error
(distractor/identity-failure) population the docs say is a separate
mechanism from the precision model, not something a covariance scale fixes.

**Fix**: `cfg.fusion.loma_cov_scale` / `samh_cov_scale` (default 1.0,
multiplicative, applied to each branch's covariance before the disagreement
check and the trace tie-break). New config
`corner_fusion_alignh_calibrated.py` (scale 32.0 / 70.0, rounded from the
measurement above). Explicitly documented as a sample-specific point
estimate from n=20 sequences, not a full calibration campaign. 2 new tests
(scale-flips-a-tie-break test is the load-bearing one). Mid-scale probe
rerun with the calibrated config: submitted 11326629 (run) / 11326630
(eval), watching. This is the read that says whether the calibration
diagnosis was right.

**Where this stands**: quad-free + corner-fusion is a real, working,

## 2026-08-11 (continued) — POT full-grid regression, root-caused

Followed up on the one open item from the full-grid result: why
`corner_fusion_alignh_calibrated` regresses vs `alignh_pure` on the full
POT-210 grid (95.99 vs 96.90) when the 20-seq POT probe showed them tied.

Per-sequence diff (full 210, `eval_results.json`): 11 sequences that were
perfect under `alignh_pure` (p@15=100) drop to 60-80 under fusion (total
-270pp); 3 sequences that were imperfect (60-80) get fully recovered to
100 (total +80pp); 196 flat. Net -190/210 ≈ -0.91pp, matching the
aggregate. The 20-seq probe simply didn't happen to sample any of the 11
regressed sequences (POT is 210 sequences; an 11/210 ≈ 5% failure rate is
easy to miss at n=20).

Telemetry on the two worst regressions (V13_5, V23_4, -40pp each):
`fusion_modes` is dominated by `loma_only_cov` (740/2000 and 1828/2000
corner-decisions) — meaning SAM-H's covariance was `None` on most frames,
so fusion fell back to LoMa entirely, discarding an already-correct SAM-H
estimate (confirmed: `samh_H` is finite and valid on 500/500 frames on
both sequences — `alignh_pure`'s p@15=100 on these sequences is real, the
homography itself is fine). `fusion_samh_cov` is finite on only 315/500
(V13_5) and 39/500 (V23_4) frames despite the homography always
converging.

**First hypothesis (WRONG, corrected below)**: initially suspected
`_corner_cov_from_boundary_fit`'s normal-matrix inversion failing
numerically on a low-`maskh_align_n_ok` fit (the missing-cov frames
correlated with low n_ok: median 3.0 vs the sequence's overall median
149.0 for V13_5). Checked precisely before trusting this: cross-referenced
`fusion_samh_cov` validity against `maskh_align_accepted` directly. Exact
match, zero mismatches either direction, on both sequences (V13_5: 315/500
accepted, 315/500 cov-valid, 0 accepted-but-cov-failed, 0 the reverse;
V23_4: 39/500 and 39/500, same 0/0). **The covariance computation itself
never fails on an accepted fit — it is only ever `None` when the align fit
was rejected**, which is simply `_maskh_last_corner_cov`'s reset-to-`None`
default, working exactly as designed. The numerical-robustness theory was
wrong; low `n_ok` correlates with *rejection*, not with the covariance
formula failing on an accepted fit.

**Real mechanism, verified**: the independent SAM-H sub-tracker is built
with `flow_enabled=False` (`tracker.py`, `_samh_tracker` construction) —
`self.flower` is never loaded, so `_estimate_flow_H` returns `None`
immediately (`if self.flower is None: return None`), unconditionally. So
inside the sub-tracker's own algorithm (`flow_hough.track`, "flow first,
mask_H fallback"), `flow_H` is *always* `None`; when the mask-H attempt is
also rejected this frame (`mask_H is None`), the chain falls through to
`_finalize_failure`, which returns `homography=self.state.last_homography`
unchanged — it coasts. Coasting still produces a valid, finite `samh_H`
every frame (matching the observed 500/500), but correctly carries no
*fresh* covariance, since nothing was measured this frame.

The gap: a coasted homography is usually still a decent estimate over a
single frame — it's exactly what lets `alignh_pure`'s own tracker (which
coasts identically on the same reject frames) hit p@15=100 on these very
sequences. But `fuse_corners` treats "no fresh covariance" identically to
"branch absent," discarding the coasted `samh_H` outright rather than
weighting it (even loosely) against LoMa. On a sequence where align
rejects on 37-92% of frames (V13_5, V23_4) yet the coasted trajectory is
still accurate, that blanket discard hands the frame to LoMa even when
LoMa is worse. Not a numerical bug and not a fusion-arithmetic bug — a
missing case: "unmeasured-this-frame-but-recently-good" is currently
indistinguishable from "never measured at all."

**Not implemented this session** (a real design choice, not a one-line
fix): the natural remedy is a decaying fallback covariance for a coasted
`samh_H` — e.g. inflate the last *real* covariance by some function of
frames-since-last-measurement, so a 1-frame-stale coast still gets a
reasonable (low-but-nonzero) vote while a long coast decays toward "branch
absent." Whether that decay should be calibrated from data or a fixed
heuristic, and how it interacts with the existing `loma_cov_scale`/
`samh_cov_scale` calibration, is worth a deliberate look rather than a
same-session patch.

## 2026-08-11 (continued) — coast theory killed, real cause found: no redetection

Started the batch by building the fix the previous entry proposed (decaying
covariance for a coasted SAM-H) and measuring the decay constant first, with
a new offline diagnostic, `experiments/coast_covariance_study.py` (staleness
from `maskh_align_accepted`, error vs GT per staleness bucket, no GPU).

**The measurement refuted the premise.** On the full PTi grid, a coasted
SAM-H estimate is not good-but-stale — it is simply wrong: median corner
error 180 px at one frame of staleness (vs 3.1 px on a measured frame), and
per sequence, **0 of 300** sequences have a median coasted error under 15 px,
with the coasted SAM-H beating LoMa on only 3.9% of them. The jump from 3 px
to 180 px between staleness 0 and 1 is not drift, it is selection: the
aligner rejects a frame *because* it is lost, so "coasting" and "lost" are
the same population. A decay model would add weight to an estimate that is
wrong 96% of the time. The coast implementation (config knobs, tracker
state, fusion branch, tests) was written, then reverted; the study script
stays as the evidence.

### Why the align branch is weak: recovery, not accuracy

`experiments/samh_accept_study.py` (new) takes apart the accepted-but-wrong
fits and compares them frame-by-frame against the quad run (PTi):

- **Not a corner-relabeling alias**: 0.0% of the 16.2k wrong-accepted fits
  are right under a best-rotation relabeling (best-relabeling error 162 px vs
  174 px direct — the fit is in the wrong *place*, not merely mislabeled).
- **Not weak evidence**: `n_ok` behind wrong fits 143 vs 162 for good ones.
- **Acceptance residual separates only weakly**: 1.77 px (wrong) vs 0.95 px
  (good) — hence the +0.4 pp from tightening it in the replay above.
- **It is recovery.** On the 61.7k GT frames the aligner *rejects* (and
  coasts), it is wrong on 100% — and the stateless Hough-quad branch, on the
  same frames with the same SAM3 masks, is right on **76.3%** of them
  (median error 4.1 px). The evidence is in the mask. The aligner cannot use
  it because its only initialization is its own last homography: once that
  has drifted off the object, nothing brings it back. The quad pipeline
  re-detects from the mask every frame for free.

### The fix, implemented: mask-moment redetection

`flatsam2/mask_align.py` gains `moment_pose_inits()` — a similarity transform
(centroid, principal axis, area) from the template silhouette to the current
one — and `align_mask_to_homography(..., redetect_above_residual_px=...)`:
when the last-H solve lands above the acceptance residual, re-solve from the
moment poses and keep the best fit. Moments are defined for any shape, so
this is redetection *without* the quadrilateral assumption. Extra GN solves
only fire on frames that were going to be rejected anyway, so the fast path
is untouched (asserted by a test).

The principal axis is defined only modulo pi, so both branches are tried; when
either silhouette is near-isotropic in second moments (`_MIN_ECCENTRICITY`,
0.05 — a *square* reads isotropic just as a circle does) the measured angle is
noise and the four quarter turns are tried instead. Config knob:
`hough.align_redetect_moments` (default off), used by
`configs/tracker/corner_fusion_alignh_redetect.py`.

Known limitation, visible in the unit test: the boundary objective cannot see
corner labeling, so a redetected pose can come back cyclically relabeled (the
module's documented identifiability caveat). Real data says this is rare in
the *incremental* path (0% aliases above); whether redetection introduces it
is a question for the probe run.

Tests: `tests/test_mask_align.py` 10/10 pass (4 new). `tests/test_config.py`
has 4 pre-existing failures unrelated to this work (`FlowConfig` has no
`ransac_threshold` — stale test, predates this session).

### The benchmark: `experiments/maskh_bench.py`

The SAM-H branch answers a self-contained question — *given the template
silhouette and this frame's mask, where is the object?* — and every input is
already on disk (`sam3_candidates` masks, dataset GT, frames). So it is
measurable offline, on CPU, in minutes, with every estimator seeing
byte-identical inputs.

Test set (`build`): 2778 cases — all 1004 GT-annotated POT-210 frames (POT
carries 6 per sequence) plus a seeded 6-per-sequence sample of the 300 PTi
test sequences. Each case stores its mask/GT covariates (IoU, the two one-sided
coverages, component count, GT scale/rotation/perspective, out-of-view share)
so results can be sliced by difficulty without re-reading masks. Sequences
split dev/test by name hash: **every number below that names a method is on the
held-out half**, tuning happened on dev only.

The decisive design choice is that the **initialization is a controlled
variable**, not whatever the tracker happened to produce:

| regime | init | what it tests |
|---|---|---|
| `good` | GT + 5 px per-corner noise | healthy tracking |
| `drift` | GT + 30 px | degraded tracking |
| `lost` | GT pose of a random other frame | estimate off the object |
| `cold` | the template pose | no information at all |

### What was actually broken: verification, not proposals

`flatsam2/mask_register.py` (new) replaces the single last-H solve with
propose / refine / verify. Proposals come from second-moment normalization:
whitening both silhouettes leaves exactly one free rotation
(`cov_mask = A cov_tpl A^T`), so a 24-angle sweep enumerates every affine pose
the two shapes agree on — defined for any shape, no corner/line/convexity
assumption anywhere.

Instrumenting the search (`register_probe` dumps every hypothesis it scored)
answered the question that mattered before any tuning:

| | P@15 |
|---|---|
| oracle over the search's own hypotheses (cold start) | **88.9** |
| what the method actually output | 56.1 |

**The proposals contain the right answer nine times in ten; the verifier threw
it away.** All subsequent work went there, and none went into generating more
hypotheses.

Why the verifier failed, measured on the mis-picked cases: the wrongly chosen
hypothesis has raster IoU **0.94 — as high as the correct one** (median gap
0.014; 91% within 0.05) while being 219 px wrong. That is silhouette
*aliasing*: a shape maps onto itself under its own symmetries, so the mask
cannot distinguish the pose from its half turn. 44.6% of all wrong hypotheses
are pure cyclic corner relabelings. No mask-shape score can fix this — it is an
identifiability limit, the one flagged in `mask_align`'s docstring, now
quantified.

The fix is a second, independent evidence source: normalized cross-correlation
of the warped template's texture against the frame, computed only inside
`warp AND mask` so occluders and background never enter the sum. Ablation on
dev, cold start: mask-only 65.9 -> **81.5** with texture.

Ranking rules were then chosen on dev against the search's oracle rather than
guessed. Findings: raster IoU beats every precision-weighted F-measure tried,
and the fit residual is a *weak* ranker (43.3 P@15 alone vs 69.2 for IoU) —
independently reproducing this file's earlier "acceptance residual separates
only weakly" result. Final score `IoU^2 * ((1+ncc)/2)^0.5`.

Two arbitration knobs, both swept on dev: a fast path (take the incumbent
outright when its score >= 0.70, which also skips the search on ~79% of healthy
frames) and an incumbent margin (a challenger must beat the last-frame pose by
40%). Without the margin the search *costs* accuracy while tracking is healthy,
because aliases score within a percent of the truth and ties break at random on
frames that were already right.

### Occlusion: measured, and mostly not a registration problem

On the 78 of 2778 cases where the SAM3 mask covers under 85% of the GT quad,
**every** method collapses — Hough 6.4, `align` 0.0, and the registration
search's own *oracle* 3.2. When the mask is not on the object, no mask->H
estimator can help; this is a segmenter failure wearing an occlusion costume,
and it bounds what any work in this module can claim.

What registration *can* do there is decline: the score drops, so the frame is
gated out rather than fused in wrong (unit-tested).

One real occlusion mechanism was found and fixed in the objective: a hidden
stretch of outline produces large residuals that Huber only *down-weights*, so
the solve still gets dragged onto the occluder's cut edge — 86 px off an
exactly-correct pose on a one-third-occluded synthetic mask. Dropping the worst
tail outright (`trim_fraction`) removes the pull entirely. It is nevertheless
**off by default**: swept on dev it costs more than it buys everywhere else
(at 0.10: good +1.7, but drift -3.8, cold -4.9, P@5 -10), because a fit allowed
to ignore its worst quarter is also happy to explain only part of the
silhouette. Kept as a documented knob for a future two-stage design (converge
untrimmed, polish trimmed).

### Cost

Profiled, not guessed: Gauss-Newton was 71% of runtime, and its innermost
operation (bilinear sampling of the SDF along the warped boundary, run nine
times per iteration for the numeric Jacobian) was four fancy-indexed numpy
gathers. Replacing it with a single `cv2.remap` and dropping a per-call
allocation in the warp took a cold-start registration from 202 ms to 120 ms;
both changes live in `mask_align` so the deployed aligner got faster too.
Healthy frames take the fast path and cost one GN solve, as before.

| `loma_samh_decoupled_rerun` (quad switch) | 65.44 | **87.86** | 89.43 | 1.57 | **92.74** | **97.66** | 0.00 |
| `corner_fusion_alignh_calibrated` | 60.97 | 80.59 | 80.65 | 0.05 | 91.26 | 95.99 | 0.00 |

(`gap` = `mean_br_p@15 - mean_p@15`, the free alias detector; % of sequences
carrying more than 5 pp of it: quad 6.7, register 11.3, **kp 9.3**, on POT
0.0 / 0.5 / 0.0.)

What the added term did, and did not, do:

- **It is an aliasing fix, and it works as one.** PTi br@15 barely moves
  (89.36 → 89.57) — the registrar was already finding the object. The gap
  closes instead, 2.83 → 2.25, on 9.3% of sequences rather than 11.3%. Direct
  p@15 gains 0.79 pp almost entirely by getting corner *labels* right on
  sequences it had already localized.
- **The effect is narrow and one-sided.** PTi: better on 11.3% of sequences,
  worse on 2.3%, flat on 86.3%. Wins are large where they land (Seq_00953
  +43.5, Seq_00435 +26.3, Seq_00154 +24.6); the single real loss is Seq_00931
  −9.6. That asymmetry is what "propose, don't trust" buys — a bad `loma_H` is
  outscored rather than adopted.
- **POT is flat to marginally negative** (96.77 → 96.65, −0.12 mean). 98.6% of
  sequences are unchanged; the delta is two sequences (V23_6 −25.0, V11_7
  −20.0) against one (V23_7 +20.0). POT had no aliasing left to fix — its gap
  was already 0.10 — so there was nothing here for the term to win, and n=3
  changed sequences is noise, not a cost.

Against the quad-based switch baseline the quad-free tracker now sits at
**−0.54 pp PTi p@15** (87.32 vs 87.86; better on 34.3% of sequences, worse on
29.3%) and **+3.19 pp PTi p@5** (68.63 vs 65.44), with **higher br@15 than the
quad baseline** (89.57 vs 89.43). Read together those three say the same thing:
the quad-free branch localizes the plane at least as well as the quad does, is
tighter where it lands, and every remaining point of deficit is corner
labelling — not detection, not accuracy. POT keeps a −1.01 pp deficit (96.65 vs
97.66) on 6.2% of sequences.

The aliasing that is left is now small enough that `br_p@15` is the only place
it is visible, and the natural next question is whether it is *reducible* at all
from mask+keypoint evidence or whether those sequences are genuinely ambiguous
(near-square, near-symmetric textures). The `corner_fusion_register_noapp`
ablation currently running answers the complementary question — how much of the
current disambiguation the texture verifier is responsible for.

## 2026-08-12 — appearance ablation: texture is what names the corners

`corner_fusion_register_noapp` — `corner_fusion_register` with
`register_appearance_power=0`, so hypotheses are ranked on raster IoU alone —
completed 300 PTi + 210 POT. It is a one-term controlled ablation; everything
else is inherited.

| config | PTi p@5 | PTi p@15 | PTi br@15 | gap | %seq>5pp | POT p@15 | POT gap |
|---|---|---|---|---|---|---|---|
| `corner_fusion_register` | 67.94 | **86.52** | 89.36 | 2.83 | 11.3 | **96.77** | 0.10 |
| `corner_fusion_register_kp` | 68.63 | 87.32 | 89.57 | 2.25 | 9.3 | 96.65 | 0.00 |
| **`corner_fusion_register_noapp`** | 64.36 | 81.65 | 88.67 | **7.02** | **27.0** | 95.00 | 0.89 |
| `corner_fusion_alignh_redetect` (no texture check at all) | 58.94 | 74.47 | 84.97 | 10.50 | 35.0 | 92.46 | 1.27 |

Turning texture off costs **4.87 pp** of PTi p@15 and 1.77 on POT. The
interesting part is *where* it goes:

- **br@15 barely moves**: 89.36 → 88.67, only −0.69. Shape evidence alone still
  puts the quadrilateral in the right place.
- **The gap absorbs the rest**: 2.83 → 7.02 pp, on 27.0% of sequences instead of
  11.3%. So **86% of the appearance term's value (4.18 of 4.87 pp) is corner
  *labelling*, not detection** — precisely the claim the ablation was written to
  test, now measured end-to-end rather than only on the offline benchmark.
- The prediction on record was that the gap would "open up toward the 10.50 pp /
  35% that mask-moment redetection showed". It landed at 7.02 / 27.0% — about
  two-thirds of the way, the remainder being the refinement and arbitration that
  `noapp` still keeps and `redetect` never had.

Per-sequence the ablation is broad, not tail-driven: worse on 39.0% of PTi
sequences, better on 11.7%, flat on 49.3%, with the worst losses total
(Seq_00795 −62.0, Seq_00247 −60.0, Seq_00498 −55.9) — the signature of a pose
snapping to a symmetry rather than degrading smoothly. POT moves much less
(92.9% of sequences flat) because it had almost no aliasing to lose: its gap
starts at 0.10 pp.

Read together with the keypoint proposal, the two disambiguating sources now
have measured worth on the same scale: texture verification is 4.18 pp of
labelling, the keypoint proposal a further 0.58 pp on top of it.
